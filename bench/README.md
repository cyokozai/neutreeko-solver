bench — 後退解析の基準計測
==========================

現行の強解決（`src/solve.jl` の `solve()`）の時間・メモリ・伝播の統計を測り、 これから試す改良（対称性で畳む、2 ビットの勝敗表、並列化、ビット並列など）と比べる物差しにする。 **アルゴリズムは変えていない。** `src/` には手を入れず、内訳が要る箇所は同じ手順を `bench/baseline.jl` の中で段階ごとに呼び直して測っている。段階版・計数版の表が `solve()` の表と 全局面で一致することを毎回確かめ、一致しなければ計測を止める。

| ファイル                | 中身                                                                 |
|-------------------------|----------------------------------------------------------------------|
| `baseline.jl`           | 計測の本体。TOML と Markdown の表を書く                              |
| `run_baseline.sh`       | `baseline.jl` をコンテナで走らせ、ホスト側の情報も一緒に記録する入口 |
| `results/baseline.toml` | 実測値（機械可読）。実行環境・各回の生の値（`samples`）も入る        |
| `results/baseline.md`   | 同じ実測値の表                                                       |

実行方法
--------

ホストに Julia は要らない。Docker だけで動く。依存は標準ライブラリ（TOML・CRC32c・Random・Printf）のみ。

```sh
bench/run_baseline.sh                    # 5 回反復、bench/results/baseline.{toml,md} に書く
bench/run_baseline.sh --reps 7           # 引数は baseline.jl へそのまま渡る
CPUS=4 bench/run_baseline.sh             # docker run --cpus 4 で CPU の割当を絞る
OUT=bench/results/after_x.toml bench/run_baseline.sh   # 改良後の結果を別名で残す
WAIT_IDLE=0 bench/run_baseline.sh        # 他のコンテナが落ち着くのを待たずに始める
```

`run_baseline.sh` は既定で、他のコンテナの合計 CPU が `IDLE_MAX_CPU`（既定 5）% 未満の記録が 3 回続くまで待ってから始める（`IDLE_TIMEOUT` 秒、既定 1800 で中止）。始めた後に他のコンテナが動き出した場合は、結果の表に注意書きが出る。

`run_baseline.sh` を通さずに直接走らせてもよい（そのときホスト側の情報と `docker stats` は記録されない）。

```sh
docker run --rm -v <リポジトリの絶対パス>:/work -w /work julia:1.11 \
    julia --project=. bench/baseline.jl --out bench/results/baseline.toml
```

`baseline.jl` の引数:

| 引数                | 既定                          | 意味                                                     |
|---------------------|-------------------------------|----------------------------------------------------------|
| `--out PATH`        | `bench/results/baseline.toml` | TOML の出力先。拡張子を `.md` に替えた名前で表も書く     |
| `--reps N`          | 5                             | 各項目の反復回数（JIT 込みの初回を除いた回数）           |
| `--fixpoint-reps N` | `--reps` と同じ               | `solve_fixpoint()` の反復回数                            |
| `--threads LIST`    | `1,8`                         | スレッド数の確認で起こす子プロセスの `-t`。`none` で省略 |
| `--rule draw\|loss` | `draw`                        | 合法手 0 の扱い                                          |

一通りで 2〜3 分かかる（うち `solve_fixpoint()` が 5 回 × 約 6 秒）。

何をどう測ったか
----------------

### 計時の方法

外部パッケージ（BenchmarkTools など）は使わない。各項目を次の手順で測る（`measure`）。

1.	1 回走らせて捨てる（JIT コンパイルを除くため）。
2.	`GC.gc()` で前の回のごみを片付けてから `@timed` で 1 回測る。これを `--reps` 回繰り返す。
3.	経過時間・割り当てバイト数・GC 時間それぞれの中央値・最小・最大を記録する。各回の生の値は TOML の `samples` に残す。

比べるときは**中央値**を主に見る。最小は「邪魔が入らなかったときの値」、最大はばらつきの目安。

### 項目

| 区分       | 項目                                                                                                                                                 | 測り方                                                                                                                                                                                                             |
|------------|------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 時間       | `solve()` 全体                                                                                                                                       | 公開の `solve()` をそのまま呼ぶ                                                                                                                                                                                    |
|            | 内訳                                                                                                                                                 | `solve()` と同じ手順を 4 段階に割って `time_ns()` で挟む。1. 分類＋カウンタ初期化（`initial_labels` をそのまま呼ぶ）、2. 終局をキューに積む、3. キュー伝播（`solve()` の while ループを写したもの）、4. 引分け確定 |
|            | 分類の中身（参考）                                                                                                                                   | `initial_labels` の 1 本のループを「unrank＋`state_kind`」と「内部局面の `count_moves`」に割って別々に測る。足しても段階 1 とは一致しない（ループと unrank が二重になる）                                          |
|            | `solve_fixpoint()`                                                                                                                                   | 前向き不動点反復（比較用）。反復回数は「最大距離＋1」（反復 j で距離 j の局面が確定し、最後の 1 回で何も変わらない）                                                                                               |
| 伝播の統計 | 取り出した局面数・列挙した直前局面の総数・未確定だった直前局面・カウンタ減算の回数・勝ち／負けの確定数・距離ごとの層の大きさ・キューの未処理分の最大 | 伝播ループに計数を足した版で 1 回数える。層ごとの時間はこの版で取るので、計数の分だけ膨らんだ参考値                                                                                                                |
| メモリ     | 表（`value`・`dist`）と作業配列（`cnt`・キュー）のバイト数                                                                                           | 型と局面数から計算（`sizeof`）                                                                                                                                                                                     |
|            | `@allocated` と GC 時間                                                                                                                              | `@timed` の `bytes` と `gctime`                                                                                                                                                                                    |
|            | 最大常駐量                                                                                                                                           | `Sys.maxrss()` と `/proc/self/status` の `VmHWM`・`VmRSS` を計測の区切りごとに取る。solve() だけの常駐量は、子プロセス（スレッド確認用）で「solve() 前の VmRSS」と「solve() 後の VmHWM」の差を見る                 |
| 番号付け   | `rank_state` / `unrank_state` 1 回あたりの ns                                                                                                        | 全 3,542,000 局面を番号順と無作為順で 1 周する                                                                                                                                                                     |
| 手の生成   | `foreach_child` / `foreach_predecessor` 1 局面あたりの ns と平均分岐数                                                                               | 前向きは内部局面、後ろ向きは有効局面と「勝ち負けが確定した局面」（`solve()` が実際に取り出す集合）で 1 周する。生成だけの版と、生成した局面に `rank_state` まで掛ける版の二通り                                    |
|            | 8 対称の正規形番号（参考）                                                                                                                           | 無作為 100 万局面で、8 変換の最小番号を求める時間。対称で畳む案を検討するときの下調べ                                                                                                                              |
| 参照       | `lookup(t, p)` の ns                                                                                                                                 | 無作為な有効局面 100 万個（手番の色も無作為）。あわせて `t.value[state_index(p)]` と `best_moves`                                                                                                                  |
| スレッド   | `-t 1` と `-t 8` の比較                                                                                                                              | 同じスクリプトを `--probe` で子プロセスとして起こし、`solve()` の時間と表の CRC32c を比べる。現行の `src/` にスレッドを使う箇所は無いので、時間は変わらず表も一致するはず                                          |

最適化で計測対象が消されないよう、各関数は戻り値（畳み込んだ和など）を返し、それを大域の `SINK` に流している。

### 注意点

-	**`Sys.maxrss()` は子プロセスでは使えない。** Linux の `getrusage` の最大常駐量は `exec` をまたいで親の値を引き継ぐので、子プロセスでは親の最大値がそのまま出る。子プロセスの常駐量は `VmHWM` で見る。
-	主プロセスの常駐量には Julia 本体（約 350 MiB）と、番号付けの計測で作る作業配列（全局面の `me`・`opp` など）が含まれる。solve() そのものの増分は子プロセスの差で見る。
-	層ごとの時間は計数版のもので、合計は `solve()` より大きい。層どうしの割合を見るのに使う。
-	Apple Silicon では高性能コアと高効率コアが混在する。他の処理が高性能コアを使っていると、計測が高効率コアに回って遅く出ることがある。

実行環境の記録
--------------

`run_baseline.sh` は次をホスト側で集めて環境変数でコンテナに渡し、TOML の `[environment]` に記録する。

| 記録                                                                      | 取り方                                                                                                                                                               |
|---------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| コミット・`src/` の tree ハッシュ・`src/` の未コミット変更の数            | `git rev-parse HEAD` / `git rev-parse HEAD:src` / `git status --porcelain -- src`                                                                                    |
| ホストの CPU・論理コア数・コア種別・メモリ・OS                            | macOS は `sysctl`（`machdep.cpu.brand_string`・`hw.ncpu`・`hw.perflevel{0,1}.logicalcpu`・`hw.memsize`）、Linux は `/proc/cpuinfo`・`nproc`・`/proc/meminfo`         |
| Docker の VM に割り当てた CPU・メモリ、実行環境の名前                     | `docker info`（`NCPU`・`MemTotal`・`OperatingSystem`）                                                                                                               |
| `docker run` の CPU 指定                                                  | 環境変数 `CPUS`（`--cpus`）と、コンテナ内の `/sys/fs/cgroup/cpu.max`                                                                                                 |
| 他のコンテナの CPU 使用                                                   | 計測直前に `docker stats --no-stream`、計測中も `STATS_INTERVAL` 秒（既定 10）ごとに取り、名前ごとの最大と「自分以外の合計」の最大を記録する。生の記録も TOML に残る |
| Julia の版・スレッド数・アーキテクチャ・コンテナから見える CPU 数とメモリ | コンテナ内の `VERSION`・`Threads.nthreads()`・`Sys.*`                                                                                                                |

**他のコンテナが CPU を使っている状態で測った値は比較に使わない。** `docker stats` の記録で自分以外の合計が数 % を超えていたら、落ち着いてから測り直す。改良後の計測も同じ機械・同じ Docker の割当で行い、`src_tree` で対象のコードを確かめてから比べる。
